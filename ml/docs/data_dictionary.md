# Hospitality Operations Intelligence data dictionary (ALL DATA SYNTHETIC)

Every table here is SYNTHETIC: generated by the seeded generator in `ml/generator/` (seed in
`ml/generator/config.yaml`) from ASSUMED parameters. None of it describes a real hotel or
person. Employees are ids only; no names, gender, age, religion, caste, health or family status
exist anywhere.

Markers used below:
- **[HIDDEN]**: generator-only; never read by models, evaluation, backend or frontend.
- **[DERIVED]**: computed from other tables (not drawn from the generator directly).
- **[LABEL]**: an outcome. Use it only as a target, or from weeks before the prediction date.
- **[DEMO]**: scripted demo-only data, never used for training or testing.

Dates are `YYYY-MM-DD`. Weeks start on Monday (`week_start`). The horizon is 2023-01-01 to
2029-12-31 (festival dates for 2026-2029 are unverified approximations).

## Daily tables (join on `date`)

### `data/event_calendar.csv`: one row per day
| column | type | meaning |
|---|---|---|
| date | date | calendar day |
| day_of_week | int | Mon=0 .. Sun=6 |
| month | int | 1-12 |
| is_weekend | bool | Friday or Saturday (hotel weekend) |
| is_public_holiday | bool | national / state public holiday |
| festival_name | str | festival(s) on the day, `"; "`-joined, empty if none |
| is_festival | bool | a festival falls on the day |
| is_festival_window | bool | 3 days before to 1 day after a festival day |
| is_char_dham | bool | inside the Char Dham pilgrimage season (peak demand) |
| is_school_holiday | bool | school holiday period |

### `data/weather_daily.csv`: one row per day
| column | type | meaning |
|---|---|---|
| date | date | day |
| temp_c | float | mean temperature, deg C |
| rain_day | bool | measurable rain |
| heavy_rain | bool | heavy rain (subset of rain days) |

### `data/occupancy_daily.csv`: one row per day
| column | type | meaning |
|---|---|---|
| date | date | stay date |

## Staff tables

### `data/employee.csv` (Task 3 initial staff) and `data/employee_v2.csv` (with replacement hires)
Same columns. **Models read employee_v2.csv.** The first rows of v2 equal employee.csv; every
replacement hire follows (ids continue, never reused).
| column | type | meaning |
|---|---|---|
| employee_id | str | `E001`.. (heroes use `H9xx`, see demo) |
| department | str | housekeeping, kitchen, front_office, fnb_service, maintenance, security |
| role | str | head, supervisor, attendant, cook, head_chef, helper, waiter, captain, receptionist, concierge, technician, guard |
| is_department_head | bool | heads the department |
| manager_id | str | department head's id at hire time; empty for heads. No relationship signal exists |
| hire_date | date | first day; can fall after the last simulated week for a scheduled hire |
| contract_type | str | permanent or seasonal |
| contract_end_date | date | end of the contract AT HIRE (seasonal only; renewals in contract_renewals.csv) |
| monthly_pay | int | pay at hire, INR (later changes in pay_changes.csv) |
| last_raise_date | date | last raise before the simulation (hire date if none) |

### `data/employee_skill.csv`
Every employee in employee_v2 (original staff and replacement hires; replacement hires were added
by a bug fix after T12b: `ml/generator/run_skills.py`).
| column | type | meaning |
|---|---|---|
| employee_id | str | employee |
| skill | str | skill name |
| level | int | 1-3 |

### `data/dept_week_load.csv` (static, Task 3) and `data/dept_week_load_dynamic.csv` (follows exits / hires)
| column | type | meaning |
|---|---|---|
| week_start | date | Monday |
| department | str | department |
| occupied_room_nights | int | room nights sold in the week [DERIVED from occupancy] |
| required_hours | float | hours of work needed (calibrated placeholder standards) [DERIVED] |
| headcount | int | staff in the department (dynamic: changes the week after an exit / hire) |
| available_hours | float | headcount x standard weekly hours (dynamic: days employed / 7) [DERIVED] |
| load_ratio | float | required_hours / available_hours [DERIVED; LABEL for the workload model] |

### `data/weekly_behaviour.csv`: one row per employee per week employed
| column | type | meaning |
|---|---|---|

| load_ratio | float | the department's dynamic load that week |
| overtime_hours | float | overtime worked that week |
| pulse_score | float | weekly pulse survey, 1-5 [LABEL for the pulse model next week] |
| leave_days | int | leave days taken that week |

### `data/weekly_signals.csv` (T5): one row per weekly_behaviour row

### `data/attrition_calibration.json` [DERIVED]
Calibrated exit-hazard intercept, achieved vs target annual attrition, simulations run, search
mode and the config fingerprint (lets the generator reuse a calibration).

### `data/internal/employee_latent.csv` [HIDDEN] (gitignored)
employee_id, overtime_propensity, baseline_pulse, baseline_task_score, latent_frustration.
Hidden traits that drive the simulation. Only `ml/generator` may read this file.

## Demo tables [DEMO]

`data/demo/hero_employees.csv` (employee_v2 columns) and `data/demo/hero_weekly.csv`
(weekly_behaviour + weekly_signals columns): five scripted, fictional heroes H901-H905 over the
last 12 weeks, from `ml/generator/heroes.yaml`. `data/demo/hero_display_names.json` maps ids to
first names for the demo screens only. Heroes are appended to the tables at SCORING time only.

## Model feature matrices [DERIVED] (built in memory or gitignored)

### Attrition (`ml/attrition/features.py`, one row per active employee-week)
Ids: employee_id, week_start. Categorical: department, role, contract_type. Numeric:
is_department_head, tenure_days, monthly_pay (in force), pay_ratio (pay / role mean),
months_since_raise, load_ratio, overtime_hours, overtime_roll4_mean, overtime_window_mean (10
weeks), leave_days, weeks_without_leave, pulse_score, pulse_roll4_mean, pulse_trend_4w,
peer_exits (department exits in the last 8 weeks), days_until_contract_end (capped at 90),
weeks_since_weekend_off, consecutive_days_worked, weekly_off_skipped_4w,
task_score_roll4_mean, task_score_trend_4w, festival_leave_days_12w. All are trailing (own
rows up to the week; pay, raises and renewals dated on or before the week).
Labels [LABEL]: label_resignation, label_contract_end (exit of that kind in the 90 days after
the week); is_censored = the 90-day window runs past the data (excluded from training and test).

### `data/pulse_features.csv` (gitignored)
employee_id, week_start, department, role, contract_type, tenure_days, load_ratio,
overtime_hours, leave_days, pulse_score, pulse_roll4_mean, pulse_trend_4w,
days_until_contract_end; label next_week_pulse_score [LABEL].

### `data/workload_features.csv` (gitignored)
department, week_start, week_of_year, occupied_room_nights, load_ratio, headcount,
load_roll4_mean, room_nights_roll4_mean, load_trend_4w, is_festival_week,
next_week_is_festival (published calendar, not leakage); label next_week_load_ratio [LABEL].

### Occupancy forecast (`ml/forecast/core.py`, one row per target day per horizon)
Target-day calendar flags; occupancy history at the origin (occ_origin, 7 / 28-day means, same
weekday 52 weeks before); weather up to the origin; for horizons <= 7 days also
occ_target_minus_7 and booking_pace_7d / rooms. Baseline: seasonal_naive (same weekday 52 weeks
before). Target: target_occupancy [LABEL].

## Output / mock files (T9-T12b)

The public interfaces return Pydantic types (`ml/forecast/api.py`, `ml/attrition/api.py`,
`ml/voice/api.py`); every result carries `synthetic: true`. `python run.py mocks` (also run by
`eval`) writes them to `ml/data/mocks/` for the frontend, with field names identical to the
types:

| file | type | content |
|---|---|---|
| `forecast_week.json` | ForecastResult | `as_of`, `band`, `days` (date, horizon_days, source, mean, low, high, high_demand_alert, low_demand_alert) for the last week of data |
| `attrition_scores.json` | list[AttritionScore] | every active employee (staff and demo heroes) in the latest scoring week |
| `rescore_sunita.json` | RescoreResult | Sunita (H901) before / after two protected weekends off: overrides, features_before, features_after, before, after, risk_change, note (a SIMULATION, not causal proof) |
| `heroes.json` | list[HeroInfo] | employee_id, display_name (fictional, demo-only), department, role, contract_type, story [DEMO] |

### AttritionScore fields
| field | meaning |
|---|---|
| employee_id, week_start | key |
| segment | resignation (permanent staff) or contract_end (seasonal staff) |
| model | the scoring model (the segment's winner: logistic / contract_rule) |
| risk | calibrated probability of an exit in the next 90 days [DERIVED] |
| rank | 1 = highest risk among active non-hero staff of the same group that week; tied staff share a rank [DERIVED] |
| group_size | number of active non-hero staff in that group that week |
| band | high / watch / low |
| band_basis | `model_rank` (permanent: high = first ceil(10% x n) rank slots, watch = next ceil(15% x n), tie groups never split) or `contract_date_rule` (seasonal: days to contract end <= 30 high, <= 60 watch) |
| rank_is_tied | true when other staff share the same (4-decimal) risk; common for seasonal staff |
| is_demo_hero | true for the scripted heroes, who are placed against the staff and never take a slot [DEMO] |
| drivers | up to 3 driver categories, each with category, title, reason (plain language), `contribution_logodds` (from the scoring model, calibrated log-odds vs the training mean) and `support_level` (supported / weakly_supported) |
| actions | the top driver's 2 playbook interventions: driver, action, owner, check_after_weeks, expected_effect (an ASSUMPTION) |
| synthetic | always true |
